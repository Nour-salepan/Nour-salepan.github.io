Nmap Crash Course: Scanning a Vulnerable Web App From Scratch

Every Nmap flag that actually matters, in the order you'd use them — worked end to end against a deliberately vulnerable application until it hands over its database password.

Most Nmap tutorials hand you a wall of flags and leave you there. This one runs a single scan sequence against a real target, end to end, and shows you the moment it stops being a port list and becomes an actual vulnerability.

The target is DVWA — the Damn Vulnerable Web Application — running on my own machine. By the end we'll have gone from "is this host even alive" to holding its database username and password, using nothing but Nmap and a browser.

Part 01Read this first: the legal part

Not optional

Port scanning a system you don't own or have written permission to test is a crime in most countries — including when nothing breaks and you meant no harm. Intent is not a defence. "I was learning" is not a defence.

Legitimate targets, and this list is basically exhaustive for a beginner:

  • Your own machines — a VM or container on your laptop
  • scanme.nmap.org — run by the Nmap project explicitly for this, though don't hammer it
  • TryHackMe, Hack The Box, PortSwigger Labs — purpose-built and authorised
  • A client who has signed a scope document — once you're doing this professionally

Everything below runs against localhost. Nothing leaves my machine. Develop that habit now, because the difference between a security analyst and a defendant is paperwork.

Part 02Build the lab

You need two things: Nmap, and something to point it at.

# install nmap $ sudo apt install nmap # Debian / Ubuntu / Kali $ brew install nmap # macOS # confirm it's there $ nmap --version # spin up DVWA locally on port 8080 $ docker run --rm -it -p 8080:80 vulnerables/web-dvwa

That's the whole lab. A deliberately broken web app, reachable only from your own machine, that you can scan as aggressively as you like.

Part 03How scanning actually works

Before the flags, the mental model — because without it the output is noise.

A port is a numbered door on a machine, 1 through 65535. A service sits behind a door and listens. Web servers usually listen on 80 or 443, SSH on 22, and so on. Scanning is the process of knocking on doors and recording which ones answer.

The knock itself relies on the TCP three-way handshake — how every TCP connection on the internet begins:

01

SYN

are you open?

02

SYN-ACK

yes, I'm here

03

ACK

connection made

04

RST

or: go away

A SYN scan (-sS) sends the first packet, reads the reply, and then deliberately never completes the handshake. Faster, and historically quieter in logs. It needs root. A connect scan (-sT) completes the full handshake using the operating system's normal networking, which needs no privileges but is slower and far more visible.

Nmap reports each port in one of these states, and the ambiguous ones matter:

StateWhat it means
openSomething is listening. This is what you're hunting.
closedThe host replied, but nothing is listening there. Still useful — it proves the host is alive.
filteredNo reply at all. A firewall is probably swallowing the packets. You've learned something about the defences, not the service.
open|filteredNmap genuinely can't tell. Common in UDP scans.
The distinction worth internalising

closed means the door exists and is shut. filtered means something is stopping you from even reaching the door. Beginners treat both as "nothing there" and miss that filtered tells you a firewall exists.

Part 04Stage 1 — Is anything there?

Host discovery. Don't scan 65535 ports on a machine that's switched off.

$ nmap -sn localhost Starting Nmap Nmap scan report for localhost (127.0.0.1) Host is up (0.000090s latency).

-sn means "ping scan, skip the ports." On a network you'd sweep a whole range — nmap -sn 192.168.1.0/24 — to map what exists before touching anything.

The inverse flag is -Pn: skip discovery, assume it's up. Reach for it when a host blocks pings but you're confident it's alive — otherwise Nmap gives up before scanning a perfectly live machine.

Part 05Stage 2 — Which doors are open?

By default Nmap checks the 1000 most common ports. That's a reasonable start and an unreasonable finish.

# default: top 1000 ports $ nmap localhost # all 65535 — slower, but finds the things hiding high up $ nmap -p- localhost # specific ports $ nmap -p 80,443,8080 localhost # a range $ nmap -p 1-1000 localhost # quick triage: top 100 only $ nmap --top-ports 100 localhost

Against our DVWA box, the full scan returns exactly one door:

$ nmap -p- localhost PORT STATE SERVICE 8080/tcp open http-proxy

One open port. The SERVICE column here is a guess — Nmap is reading port 8080 off a lookup table and assuming "probably an HTTP proxy." It has not actually checked. Proving what's really there is the next stage, and treating that column as fact is one of the most common beginner mistakes.

Scan types and speed

$ sudo nmap -sS localhost # SYN / stealth scan (needs root) $ nmap -sT localhost # TCP connect (no root) $ sudo nmap -sU localhost # UDP — slow, often skipped, often where the gold is # timing: -T0 paranoid ... -T5 insane. -T4 is the sensible default $ nmap -T4 -p- localhost
On timing

-T4 is fine on your own network. -T5 drops packets and lies to you. On a client engagement, slower is often required — fast scans trip intrusion detection and can knock fragile services over. Speed is a trade against accuracy and stealth, not a free win.

Part 06Stage 3 — What's running behind them?

This is where guessing stops. -sV interrogates the port and reads the software's own banner back.

$ nmap -sV -p 8080 localhost PORT STATE SERVICE VERSION 8080/tcp open http Apache httpd 2.4.25 ((Debian))

That one line changes everything. It isn't "probably a proxy" any more — it's Apache 2.4.25 on Debian. An exact version is a search query: an attacker pastes it into a CVE database and gets a list of known vulnerabilities for that build.

And OS detection, which needs root:

$ sudo nmap -O localhost Running: Linux 4.X OS details: Linux 4.15 - 5.6

There's a shortcut that does several of these at once: -A runs version detection, OS detection, default scripts and traceroute together. Convenient, and loud — it is not subtle and shouldn't be your first move against anything sensitive.

Part 07Stage 4 — NSE, where it gets interesting

The Nmap Scripting Engine is the part that turns Nmap from a port lister into a reconnaissance tool. Hundreds of scripts ship with it, grouped into categories — default, discovery, vuln, safe, intrusive, brute and more.

# run the default script set $ nmap -sC -p 8080 localhost # pick specific scripts $ nmap --script=http-enum,http-headers,http-methods -p 8080 localhost # a whole category $ nmap --script=vuln -p 8080 localhost # what does this script even do? $ nmap --script-help=http-enum

Here's the run that mattered. Three scripts against our one open port:

$ nmap --script=http-enum,http-headers,http-methods -p 8080 localhost PORT STATE SERVICE 8080/tcp open http | http-enum: | /login.php: Possible admin folder |_ /config/: Potentially interesting directory w/ listing | http-headers: |_ Server: Apache/2.4.25 (Debian) | http-methods: |_ Supported Methods: GET HEAD POST OPTIONS

Three separate pieces of intelligence from one command:

  • http-methods — only GET, HEAD, POST and OPTIONS. No PUT or DELETE. That's genuinely good news for the defenders; PUT can often be abused to upload a shell.
  • http-headers — the server is advertising its exact version. Minor on its own, but it's free reconnaissance handed to an attacker.
  • http-enum — and here it is: /config/, a directory with listing enabled.
The moment to pay attention

"Potentially interesting directory w/ listing" is Nmap telling you a door has been left propped open. Directory listing means that instead of a web page, the server shows you the raw contents of the folder — every file in it, by name. A folder called config is exactly where you'd expect secrets to live.

Part 08The finding: chaining two boring bugs

Nmap has done its job. The rest is a browser and about ninety seconds of thinking.

Open the directory it flagged:

http://localhost:8080/config/ Index of /config config.inc.php config.inc.php.bak config.inc.php.dist

Three files. The first is harmless — request config.inc.php and the server executes it as PHP, so you get the output, which is nothing. The source stays hidden. That's how it's supposed to work.

But .bak is not a file extension Apache knows how to execute. So when you ask for it, the server does the only thing it can: it sends you the file. As plain text.

http://localhost:8080/config/config.inc.php.bak db_user = 'app' db_password = 'vulnerables' db_database = 'dvwa'

That's the database password, read out of a web browser by an unauthenticated stranger. No exploit, no payload, no CVE. Two configuration mistakes that are individually unremarkable:

MEDIUM
Directory listing enabled — on its own, this just leaks filenames. Untidy, not fatal.
HIGH
A backup file left in the web root — on its own, this is only dangerous if someone knows the filename to guess.
CRITICAL
Both together — the listing tells you the filename, and the backup serves you the contents. Full database credentials.
This is what real breaches look like

Not a genius defeating encryption. A sequence of small, individually forgivable mistakes that line up. The Equifax breach was an unapplied patch. Countless others are an exposed backup, a default password, a storage bucket set to public.

Which is why the useful skill isn't memorising exploits — it's noticing when two unremarkable findings combine into one serious one.

The fixes, all cheap

  • Options -Indexes in the Apache config — kills directory listing
  • Delete .bak, .old and .dist files from the web root, and block those extensions at the server
  • Store configuration files outside the web root entirely, so they can't be requested at all
  • ServerTokens Prod and ServerSignature Off — stop advertising the version

Part 09Turning output into a report

Scan output is evidence, and evidence needs saving. Nmap writes to several formats:

$ nmap -sV -p- -oN scan.txt localhost # normal, human-readable $ nmap -sV -oX scan.xml localhost # XML, for tooling $ nmap -sV -oG scan.gnmap localhost # greppable $ nmap -sV -oA scan localhost # all three at once

-oA is the one to default to. Disk is cheap, and re-running a scan to recover output you didn't save is embarrassing.

But raw output is not a report. Nobody is going to act on a terminal dump. A finding needs four things, every time:

  • What — one sentence a manager can understand. "Database credentials are readable by anyone with a browser."
  • Evidence — the exact command and the exact output. Reproducible or it didn't happen.
  • Impact — the consequence, in business terms. "An unauthenticated attacker can read, alter or delete the entire database."
  • Remediation — specific and actionable. Not "improve security" but "set Options -Indexes and remove .bak files from the web root."

I wrote the DVWA assessment up this way — executive summary, severity table, methodology, then each finding with those four parts. You can read the full report here, or the case study version.

Plenty of people can run a scan. Far fewer can explain which line of the output matters and why.

Part 10Automating the whole thing

You'll run this same four-stage sequence against every target forever, which makes it a script. Here's the shape of it:

#!/bin/bash TARGET=$1 OUT="recon_$TARGET" mkdir -p "$OUT" # 1. is it alive? nmap -sn "$TARGET" | tee "$OUT/1-discovery.txt" # 2. what's open? nmap -p- -T4 "$TARGET" | tee "$OUT/2-ports.txt" # 3. what's running? nmap -sV "$TARGET" | tee "$OUT/3-versions.txt" # 4. dig deeper nmap -sC "$TARGET" | tee "$OUT/4-scripts.txt" echo "Done. Results in $OUT/"

tee is the useful trick there — it prints to your terminal and writes the file, so you watch it live and still keep the evidence.

My full version adds colour output, input validation and a per-target report folder. Both scripts are on GitHub — I wrote the plain one from scratch first, deliberately, to be sure I understood every step before letting anything generate it for me. That order matters more than it sounds: if you automate a workflow you don't understand, you can't tell when the output is wrong.

A sensible default sequence

$ nmap -sn 192.168.1.0/24 # 1. what exists $ sudo nmap -sS -p- -T4 -oA ports TARGET # 2. every door $ nmap -sV -sC -p 22,80,8080 -oA deep TARGET # 3. dig into what's open

Where to go next

  • Wireshark — run a capture while you scan and watch the handshakes happen. Nothing makes -sS versus -sT click faster than seeing the difference on the wire.
  • TryHackMe — the Nmap room, then Network Services, in an environment that authorises you
  • More DVWA — you've only done reconnaissance. The app has SQL injection, XSS, file upload and command injection waiting.
  • Write one up — take any lab, scan it, and produce a one-page report with the four-part structure from Part 09. That artefact is worth more in an interview than a certificate.

Nmap isn't hard. It's maybe fifteen flags that matter, and you've now seen all of them in the order you'd actually use them. The skill that takes longer is the one from Part 08 — looking at "directory with listing" and "a .bak file" and seeing that together they're a breach.
