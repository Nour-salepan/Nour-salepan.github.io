DVWA Security Assessment

Vulnerability Assessment · Nmap + NSE · November 2026 · Authorised local lab
complete

A full reconnaissance and configuration review of a Damn Vulnerable Web Application instance running on my own machine, documented as a formal security assessment report. The headline finding was a realistic breach chain: an enabled directory listing plus a leftover backup file together exposed live database credentials in plain text.

3 findings documented
1 rated critical
6 step methodology
8080 sole open port found
Methodology
# 1. host discovery $ nmap -sn localhost # 2. full port scan $ nmap -p- localhost # 3. service / version detection $ nmap -sV -p 8080 localhost # 4. OS detection $ sudo nmap -O localhost # 5. NSE enumeration $ nmap --script=http-enum,http-headers,http-methods -p 8080 localhost # 6. manual verification in a browser
Target profile
OPEN PORT8080/tcp (http)
WEB SERVERApache/2.4.25 (Debian)
OSLinux (Debian)
APPLICATIONDVWA v1.10 (PHP)
HTTP METHODSGET, HEAD, POST, OPTIONS — no PUT/DELETE
Findings
CRITICAL
Database credentials exposed via directory listing. Directory listing was enabled on /config/, allowing a browser to reach config.inc.php.bak. Because the server doesn't execute .bak as PHP, it served the file as plain text — revealing the database username, password and schema to an unauthenticated visitor.
Remediation: disable directory listing (Options -Indexes), remove backup files from the web root, store config outside the web root.
HIGH
Backup and template files left on the server. /config/ also contained config.inc.php.dist. Any extension the server won't execute gets served as source, exposing code and secrets the live .php file would hide.
Remediation: remove .bak/.old/.dist files; block those extensions at the web server.
MEDIUM
Web server version disclosure. HTTP headers returned the exact version (Apache/2.4.25 (Debian)), shortcutting an attacker's search for version-specific CVEs.
Remediation: ServerTokens Prod and ServerSignature Off.
Why this one matters — neither the directory listing nor the backup file is dramatic on its own. Chained, they hand over the database. Most real breaches look like this: a sequence of small misconfigurations, not a single exotic exploit.
Scope & ethics

Performed entirely against a deliberately vulnerable application running on my own machine. No third-party systems were scanned at any point.

Nmap Reconnaissance Toolkit

Bash · Nmap · November 2026 · Self-directed project
complete

A command-line toolkit that automates the standard reconnaissance workflow and saves the output of each stage. I wrote two versions deliberately: a plain one built entirely from scratch to prove I understood the steps, and an improved one with colour output and per-target report folders.

The workflow it automates
01

Host discovery

nmap -sn

02

Port scan

nmap -p-

03

Service versions

nmap -sV

04

NSE scripts

nmap -sC

Sample output
$ ./recon.sh scanme.nmap.org PORT SERVICE VERSION 21/tcp ftp tcpwrapped 22/tcp ssh OpenSSH 6.6.1p1 Ubuntu 80/tcp http Apache httpd 2.4.7 (Ubuntu) 9929/tcp nping-echo Nping echo # each stage saved to recon_<target>/
What I learned building it
  • How IP addresses, ports and subnets actually fit together
  • The TCP three-way handshake — SYN → SYN-ACK → ACK — and why it's the thing scans manipulate
  • The difference between a connect scan (-sT) and a stealth/SYN scan (-sS), and when each is appropriate
  • Service version detection (-sV) and OS fingerprinting (-O)
  • Using the Nmap Scripting Engine for deeper enumeration than a port list
Honest attribution

recon-simple.sh is entirely my own. In recon.sh I used an AI assistant for the colour-formatting code; the scanning logic and testing are mine. Targets are limited to my own lab, scanme.nmap.org, and authorised platforms like TryHackMe.
